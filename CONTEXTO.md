### Stack do CRM (importa para extrair)

- Laravel + **Livewire 3** + **Filament** nas telas de listagem.
- As páginas de listagem **não trazem as linhas no HTML inicial** — são renderizadas pelo Livewire depois. Um `fetch()` cru na URL devolve a casca, sem dados.
- O caminho estável é manipular o componente pelo `$wire`:
  ```js
  const w = Livewire.all().find(c => c.name === 'leads-table').$wire;
  await w.set('tableFilters.funil.funil', '128');
  await w.set('tableRecordsPerPage', 'all');
  ```

- **Tags ativas:** `#tagsSelect2 option[selected]` — um `<select multiple>` do select2 com as 29 tags disponíveis; só as marcadas têm o atributo `selected`. *Ler o texto visível da página devolve as 29, não as ativas — erro fácil de cometer.*
- **Plano de pagamento:** `select[name=planodepagamento] option[selected]` — campo personalizado, valores `até12x`, `36x`, `48x`, `Alongado` **até 02/09/2026**. ⚠️ **O CRM removeu esse campo da ficha em algum momento entre 02/09 e 03/09/2026** — o seletor não encontra mais nada e o campo vem sempre vazio (ver seção 3). **Conta separado das tags** (quando existia).

### Armadilhas descobertas na prática

1. **A aba do Chrome trava** se você renderizar as 151+ linhas (`perPage: 'all'`) *e* disparar dezenas de `fetch` em paralelo. Solução: capturar as linhas, **voltar `perPage` para 5**, e só então buscar as fichas em lotes de 4, com `d.body.innerHTML=''` após cada parse para liberar memória. Persistir em `localStorage` a cada etapa para não perder tudo num travamento.
2. **`w.set('paginators.page', N)` não pagina.** O componente ignora. Use `perPage: 'all'` ou o botão "Próxima".
3. Depois que o DataTables/JS da página mexe no DOM, o componente Livewire pode **descolar e parar de responder** ao `$wire`. Recarregue a página e refaça a sequência inteira num único script.
4. **Acesso a github.com depende do ambiente do assistente, não é uma regra fixa.** Numa sessão rodando num container restrito, `github.com`/`api.github.com` ficaram bloqueados (só `alexsborne.github.io` respondia, dava para conferir deploy por `curl` mas não publicar). Já nesta máquina Windows do usuário, `github.com` e `api.github.com` respondem normalmente e há credencial git (`credential.helper=manager`) já configurada para a conta `alexsborne` — **`git clone`/`git push` funcionam direto daqui**, sem precisar do upload manual pela web. Teste sempre `curl -s -o /dev/null -w "%{http_code}" https://api.github.com` antes de decidir qual caminho usar.
5. **Ferramentas de automação de navegador não conseguem controlar diálogos nativos do SO.** Um clique real (`computer.left_click`, não `element.click()` via JS) em um link `<a download>` dispara o download, mas se o Chrome estiver configurado para "Perguntar onde salvar cada arquivo", a caixa "Salvar como" é uma janela nativa fora do processo renderer — nem `Input.dispatchKeyEvent` via CDP nem `SendKeys` do PowerShell (que roda sem sessão de desktop interativa neste setup) alcançam essa janela. Também **downloads disparados por `a.click()` via JavaScript puro** (sem gesto real do usuário) podem ser descartados silenciosamente pelo Chrome — nenhum arquivo aparece, nenhum erro é lançado. **Caminho que funciona:** extrair os dados grandes do `localStorage` em pedaços de ~900 caracteres por chamada (o `javascript_tool` trunca respostas de texto acima disso, silenciosamente, com `[TRUNCATED]`), agrupando várias chamadas por `browser_batch`, reconstruir o JSON localmente e **validar com SHA-256** comparando o hash calculado no navegador (`crypto.subtle.digest`) com o hash do arquivo reconstruído — é a única forma de garantir que a transcrição de textos longos com acentuação (nomes, e-mails) saiu byte-a-byte idêntica.

## 4. Arquitetura do painel

### Como o arquivo é montado

`src/rebuild2.py` concatena tudo num HTML só. **Não há bundler, npm ou toolchain** — é Python puro da biblioteca padrão.

```
head2.html      → <title> + <style> (todo o CSS, ~11 KB)
body2.html      → markup: cabeçalho, abas, filtros, painéis, rodapé
chart.min.js    → Chart.js 4.4.1 UMD, inline
jspdf.js        → jsPDF 2.5.1 UMD, inline
autotable.js    → jsPDF-AutoTable 3.8.2, inline
a1..a7.js       → o aplicativo, concatenado NESTA ORDEM:
                  a1, a2, a3, a4, a5, a7, a6   ← a7 vem ANTES de a6
```

> **A ordem importa.** `a6.js` termina chamando `paint()` e `apply()`, que dependem de `paintRank()` definido em `a7.js`. Inverter quebra a inicialização.

**Placeholders substituídos no build:**

| Placeholder | Vira |
|---|---|
| `__DATA__` | o array JSON dos leads (de `dados/rows.json`, campos filtrados) — 168 no momento |
| `__CATMAP__` | `dados/catmap.json` — tag → categoria |
| `__LOGO__` | `logo_b64.txt` — PNG do logo Nexo em base64 |
| `__BUILD__` | data/hora do build, fuso `America/Sao_Paulo`, formato `dd/mm/aaaa HH:MM` |
| `__EXTRACAO__` | data (sem hora) do build, mesmo fuso — usada no selo "Extraído em" do cabeçalho (`body2.html`) e na constante `HOJE` de `a1.js` (rodapé do PDF). **Adicionado em 03/09/2026** — antes desses dois lugares tinham a data `02/09/2026` escrita à mão no código-fonte, e ficaram defasados na extração seguinte até serem descobertos e corrigidos. Se for extrair os dados num dia e só rebuildar depois, `__EXTRACAO__` vai levar a data do rebuild, não a do scraping — nesse cenário, editar manualmente antes de rodar. |

**Correção de encoding (03/09/2026):** `rebuild2.py` agora abre todos os arquivos-fonte com `encoding='utf-8'` explícito. Antes disso, rodar `python3 rebuild2.py` **neste computador Windows** quebrava com `UnicodeDecodeError` (o Python nativo do Windows abre arquivos com `cp1252` por padrão, que não lê os acentos de `dados/rows.json`). O contorno documentado antes era `PYTHONUTF8=1 python rebuild2.py` — não é mais necessário, mas funciona como alternativa se `encoding='utf-8'` for removido de novo por engano.

- `Painel_Funil_de_Pasta_Nexo.html` — standalone, com `<!doctype>`, `<html>`, `<head>`. É o que vai para o GitHub (renomeado `index.html`, com metas `noindex` acrescentadas).
- `artifact_body2.html` — **sem** doctype/html/head/body, porque o artefato da Claude injeta o esqueleto. Serve só para publicar lá.

### Filtro por clique (cross-filter) — o coração do painel

Estado único em `ST`, um array de valores por dimensão:

```js

              'plano_pagamento','mes','tag','categoria','faixa','data'];
```

`tipo_imob` foi adicionado em 05/09/2026 (ver v4.10) — é a dimensão do filtro "Imobiliária" do topo (2 valores: `Lançadora`/`Mercado`). `marca` continua existindo com os 7 grupos finos (HUNA, URBS, Adão…), usada internamente por gráficos/hierarquia que precisam do nome específico (hoje só as abas Times/Times_2, desativadas) — os dois campos coexistem de propósito, não são a mesma coisa.

`rowsFor(except)` devolve as linhas filtradas **ignorando** as dimensões passadas em `except`. É isso que faz um gráfico não se filtrar a si mesmo: o gráfico de etapas chama `rowsFor('etapa')`, então continua mostrando todas as etapas, com a selecionada em cor cheia e as demais esmaecidas (`fade()`), permitindo trocar de seleção sem limpar antes. **Desde 05/09/2026, `rowsFor()` também exclui `etapa==='Desistente'` por padrão** (regra de negócio, não dimensão de filtro) — ver v4.10 abaixo.

Regras de interação, iguais às de ferramentas de BI:
- **Clique simples** substitui o valor daquela dimensão.
- **Ctrl/Cmd + clique** acumula.
- **Clicar de novo** no mesmo item remove.
- Marcas bidimensionais (célula do mapa de calor, segmento empilhado, mês×etapa) aplicam **duas** dimensões de uma vez.
- Selects do topo e cliques nos gráficos compartilham o mesmo estado, nos dois sentidos. Com mais de um valor numa dimensão, o select mostra "(N selecionados)".
- Filtros e aba ativa vão para o **hash da URL** — dá para salvar e compartilhar um recorte pronto.

### Exportação XLSX sem biblioteca

`a3.js` gera um `.xlsx` real escrevendo o pacote OOXML na mão e empacotando num ZIP **sem compressão** (método store), com CRC32 calculado em JS. São ~120 linhas. Motivo: SheetJS pesa mais de 1 MB e o arquivo precisa continuar funcionando offline. O resultado abre no Excel com cabeçalho na cor da Nexo, primeira linha congelada, autofiltro e números como número.

Todas as exportações de **tabela** leem o **DOM da tabela no momento do clique**, então respeitam automaticamente filtros, ordenação e busca ativos. Células com duas linhas foram todas separadas em colunas próprias na v4 (ex.: "Telefone do corretor" / "E-mail do corretor" na Base de Cadastros) — não há mais união por ` · ` em nenhuma exportação atual.

### Exportação de gráfico em Excel (v4.1)

Além das exportações de tabela acima, **todo gráfico ativo tem seu próprio botão "Exportar Excel"** logo abaixo (13 no total: 3 na Visão Geral, 3 em Pagamentos, 4 em Times, 3 em Perfil e Valores — Tags e Rankings estão desativadas, sem botão).

- `chartRows(canvasId)` (`a3.js`) lê `CH[canvasId].data` (labels + datasets) direto do Chart.js — **não depende de uma tabela no DOM**, funciona mesmo para gráficos que não têm tabela nenhuma por trás (a maioria). `CHART_META` mapeia cada id de canvas ao rótulo da primeira coluna (ex.: `cImob`→"Lançadora").
- `expChartXLSX(canvasId, chartTitle)` monta uma planilha com: logo da Nexo (imagem embutida via `xl/drawings`, ancorada no canto superior esquerdo — âncora `oneCellAnchor`, **não** depende de nenhuma lib), título do gráfico, cabeçalho e dados, e uma linha de rodapé: `Fonte: Painel do Funil de Pasta — Nexo Gestão Imobiliária · Aba: <aba atual> · Gráfico: <título> · Gerado em: <data/hora>`. **A cor do cabeçalho da planilha exportada é sempre a Nexo navy `#1F2A66` fixa, independente do tema escolhido na tela** — decisão deliberada, para o arquivo exportado manter identidade visual consistente não importa o tema de quem gerou.

### Temas (v4.1)

Seletor de tema (`<select id="fTema">`) no canto superior direito do cabeçalho — 5 opções: **Nexo** (padrão, navy claro), **Meia-Noite** (escuro, índigo), **Abissal** (escuro, ciano/teal), **Bordô** (claro, vinho) e **Terracota** (claro, cobre). Persistido em `localStorage` (`nexoTema`) e aplicado antes da primeira pintura (sem "flash" do tema padrão).

- Cada tema é um bloco `:root[data-theme="id"]{...}` em `head2.html`, redefinindo as variáveis CSS (`--navy`, `--navy-d`, `--navy-l`, `--ink`, `--ink-2`, `--ink-3`, `--bg`, `--card`, `--line`, `--tint`, `--tint-line`, `--stripe`, `--hdr-sub`, `--warn-bg`). O tema Nexo é o próprio `:root` (sem atributo).
- **Decisão de design importante:** `--navy` guarda a cor de **texto/acento** (precisa ser escura no tema claro, clara/vibrante no tema escuro); `--navy-d` guarda a cor de **preenchimento sólido com texto branco em cima** (botão, cabeçalho de tabela, chip "stat" — precisa continuar escura o bastante para contraste **em todos os temas**, inclusive os escuros). Antes da v4.1 os dois papéis usavam a mesma variável, o que teria quebrado o contraste nos temas escuros; `.btn`, `thead th`, `.chip.stat`, `.chip .x:hover` e `.seg button[aria-pressed=true]` foram trocados de `var(--navy)` para `var(--navy-d)` por causa disso.
- As cores de **dado** (`--s1..--s8`, `ORD`/`SER`/`CATCOLOR` em `a1.js`, e `--good`/`--warn`/`--crit`) **não mudam por tema** — continuam as mesmas validadas para daltonismo, em todos os 5 temas. Só a "moldura" (fundo, cartões, cabeçalho, texto, bordas) muda.
- `INK`/`INK2`/`LINE`/`NAVY` (constantes JS usadas pelo Chart.js para texto/grade dos eixos e pelo plugin de rótulos) deixaram de ser `const` fixo e viram `let`, recalculadas via `getComputedStyle(...).getPropertyValue('--x')` sempre que o tema muda (`applyTheme()`, `a1.js`) — sem isso os gráficos ficariam com texto escuro ilegível sobre fundo escuro nos temas Meia-Noite/Abissal.
- Trocar de tema chama `paint()` de novo para a aba atual (os gráficos são sempre destruídos e recriados pelo `build()`, então pegam as cores novas sozinhos); as outras abas pegam a cor nova na próxima vez que forem abertas.

## 6. Riscos e pendências

### Privacidade (o ponto mais sério)

A página no GitHub Pages é **pública e sem senha**, e contém:

- Nome, telefone e e-mail dos **168 clientes**;
- Nome, telefone pessoal e e-mail dos **64 corretores**.

Isso é tratamento de dado pessoal sob a LGPD, exposto a qualquer pessoa com o link. As metas `noindex` reduzem a indexação da página, mas **não impedem o acesso direto**, e o arquivo continua navegável dentro do repositório em github.com, que é indexado.

O usuário foi alertado e optou conscientemente por publicar com os dados reais. Alternativas que ficaram na mesa e não foram executadas:

- **Cloudflare Pages + Cloudflare Access** — login por e-mail, gratuito até 50 usuários. Era a opção recomendada; exige conta Cloudflare do usuário.
- **Versão anonimizada** — nome vira iniciais, telefone e e-mail saem, todos os gráficos e cruzamentos permanecem idênticos. Nunca chegou a ser gerada.

### Limitações técnicas

- **Dados congelados em 03/09/2026 12:21** (extração mais recente; a de 02/09/2026 ficou obsoleta). Não há atualização automática. Uma nova carga exige rodar as duas extrações de novo.
- Os IDs de lead usados na extração 2 (contatos) vieram de uma lista fixa da extração 1 — **leads criados depois não entram** sem refazer. Na prática, isso já aconteceu uma vez: 8 dos 61 corretores da extração de 03/09 não estavam em `contatos.tsv` e precisaram de uma rodada extra da extração 2 (documentado na seção 3).
- A ligação do assistente com o computador do usuário e a extensão do Chrome **caíram várias vezes** durante o trabalho. Se for automatizar, prever falhas e salvar estado parcial em `localStorage`.
- O contato do corretor foi casado **por nome**, comparando forma normalizada (sem acento, minúsculas). Um caso limite: `ALITZ EMPREENDIMENTOS IMOBILIARIOS - YURI YOSHIDA` aparece no campo `responsavel` de um lead como se fosse nome de pessoa — é claramente o nome da equipe digitado no lugar errado no CRM, mas o cadastro de usuário bateu por busca e o contato foi encontrado normalmente; não foi "corrigido" para outro nome, só documentado aqui.
- **`dados/csv/*.csv` (14 arquivos) estão desatualizados desde 03/09/2026** — descrevem a extração de 151 leads (02/09), não a atual de 168. Não existe script no repositório que os gere a partir de `rows.json`; foram produzidos por um processo pontual anterior. O painel HTML **não lê esses CSVs** (usa `rows.json` direto), então isso não afeta o que está no ar — mas quem for analisar os CSVs precisa saber que estão um ciclo atrás. Regenerá-los não fez parte deste update; ficou como pendência caso o usuário queira.

### Ideias que ficaram para depois

- Automatizar a atualização (GitHub Actions + um extrator autenticado, ou push por linha de comando).
- Ranking com evolução temporal — comparar posições entre duas extrações.
- Meta por lançadora e indicador de atingimento.
- Coluna de dias parado por etapa, quando houver histórico de movimentação confiável.
